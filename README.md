### 新增真机反馈与下一步

用户确认 B 不再在打开时直接退出，但一登录微博账号就闪退，此后持续闪退。登录后的状态可能让启动反复进入同一路径，具体调用栈尚未取得。

因此，B 只获得登录前启动的用户验证，未通过完整登录与微博浏览验证。原空 iCloud 容器处理仍可能留下登录后使用空数据库的路径，网络拦截也仍需排查；不能仅凭现象确定其中哪一项导致本次故障。当前先保留 App 与本地数据，等待本次登录后的最新记录再修改，不要求更换证书。

### 已有证据

原版与 15A 经同一全能签流程在新机均启动失败。签名文件代码、签名数据、资源哈希检查通过，截图设备也确实包含在描述文件中；这些不证明设备信任或实际运行成功。应用与固定签名 ID 的差异仍是观察项，不能单独断言它是闪退根因。

更具体的差异是：重签后原有 iCloud 容器列表为空，而原程序启动时在 CloudCenter 中直接获取默认 CloudKit 容器。既有异常记录包含该初始化路径。B 用于验证此线索，不宣称它已解释所有启动故障。

### B 的精确改动与限制

以 15A 为底包，只把原程序中 6 处获取默认云容器的指令改为 nil 返回。源码清单记录全部偏移与前后指令。主页框架逐字节不变，未新增库、修改系统权限或伪造授权；云功能不可用，不主动删除本地数据。

ZIP、精确变更范围、指令差异、权限保留、代码页和资源签名检查通过。ARM64 模拟检查确认这 6 处片段跳过容器调用，首次数据库初始化片段可处理 nil 结果。测试中的 CloudKit 与运行时为替身，**完整初始化、后续空数据库使用、设备启动、在线功能与显示适配均未验证**。

15A 的接口转换依据用户确认有效的 [bin64 QX 脚本](https://raw.githubusercontent.com/bin64/Scripts/main/QuantumultX/vvebo.js)。原始日志、用户签名包、描述文件、证书及设备标识不公开。
